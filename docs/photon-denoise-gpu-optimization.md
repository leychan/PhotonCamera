# Photon 降噪 GPU 调度优化

## 调试日志清理

性能确认后已移除排查期间新增的拍摄分段日志、HDRNet 分段日志、IIR 细分日志及
Photon 逐层计时。对应的 `CaptureTiming`、`PhotonDenoiseTiming`、检查点 fence、
计时等待和回读钩子也已删除；保留算法需要的 memory barrier、资源所有权同步和
原有 CPU 回读。下文的计时字段、诊断实现和实测数据作为历史验证记录保留，
不再表示当前版本会输出这些日志。

## 处理边界

优化限于重建分块、开关专门化、安全内区访问、最高两层引导结果复用及融合后 IIR 独立扫描线分组。
金字塔层数、滤波窗口、
噪声模型、三轮强度估计、降噪强度、阈值、边缘镜像、单像素浮点运算顺序及既有存储精度保持原样。
Band、base 和 pilot 继续通过整数共享内存保存打包后的半浮点位，保留原有舍入边界。
GPU 到整数纹理的量化以及后续显影、HDRNet 输入和相册保存流程不作调整。

## 输出分块

线程组仍为 `8×8`，最高两层默认覆盖 `8×8` 输出块，其余层覆盖 `8×16` 输出块。
以下给出 `8×16` 分块的几何；每个线程输出两个像素。
Band 保留四像素边界，pilot 保留两像素边界。三个共享数组分别覆盖 `16×24`、
`16×24` 和 `12×20` 个元素；按 `uvec3` 数组元素占 16 字节的保守布局计算，
总计 `384×16 + 384×16 + 240×8 = 14208` 字节。

相同输出面积下，band 邻域计算量从每输出像素四项降到三项，pilot 从 2.25 项降到
1.875 项。此为计算次数变化，不能解释为整张照片的提速比例；更大的共享数组也可能
影响具体 GPU 的并发驻留，性能以目标手机测量为准。

只有重建 dispatch 按 `8×16` 输出几何计算工作组数量；分析与估计仍沿用各自原有几何。
所有线程先完成共享数据装载和 barrier，再按输出尺寸检查两个输出位置，覆盖尾块。

最高两层默认使用 `8×8` 输出块，每个线程输出一个像素，共享内存保守占用
9344 字节。其余层保持 `8×16`。
两种分块只改变计算调度，不改变滤波或数据精度；
保留构建属性选择 `8×16`，不根据未经验证的 GPU 型号表自动选择策略。

## Shader 专门化

按原有条件解析亮度降噪、色度降噪、双边滤波和首层输入／输出开关，将其写为 GLSL
常量，其余参数继续作为 uniform。双边滤波仅在色度降噪启用时启用；首层仍执行相机
RGB 到工作空间及结果到相机 RGB 的转换。

变体按开关组合缓存，本次实际需要的变体在金字塔提交前准备。首次使用可能增加编译
开销，`stage=programs` 的 `compiled` 和 `wallMs` 单独记录该开销；热拍摄复用缓存。
诊断输出使用同一组开关和分块，仍输出 band、base、noise、pilot 供对照。

## 安全内区与边缘分区

重建的共享内存邻域读取原先都调用镜像坐标映射，含动态整数取模；图像内区的镜像
结果与原坐标相同。最高两层按工作组分为一个安全内区和至多四个边缘矩形，矩形互不
重叠且覆盖整层。内区变体的 `sampleCoordinate` 直接返回坐标，边缘变体保留原镜像。
上采样读取粗层时仍完整保留原来的镜像逻辑，不改变该段代码。

边界宽度为四像素：pilot 半径 2，加结构张量半径 1，再加中心差分半径 1。
只有整个输出工作组及其四像素邻域都位于图内，才进入内区；不足以形成内区的小图
仍整层使用边缘变体。非整工作组的尾块沿用原来的边界检查。

区域起点通过 `uTileOffset` 加到工作组 ID 后再换算像素坐标。每个区域仍先完整装载
共享内存并经过所有 barrier，才输出有效像素。各区域只读输入与粗层，写入互不重叠
的输出位置；同一变体的边缘矩形统一提交后执行 image/texture/framebuffer barrier。
变体之间同样执行 barrier，整层结束后沿用原来的 flush/yield，不加入逐区域 CPU 等待。
诊断输出与最终输出共用同一分区计划。

## 最高两层的引导结果逐像素复用

仅在 L0、L1 原本启用亮度降噪时，将融合式重建拆成 `PILOT → FINAL`。
其余层及亮度降噪关闭的路径仍使用原融合实现。两个步骤共用原来的 `computeBand`、
`computePilot`、`computeFinal` 和权重函数，不改变窗口、相位、模型、阈值或累加顺序。

`PILOT` 的 band 共享内存保留两像素邻域，满足核心引导计算的结构张量和加权窗口。
每个工作组仅计算自己的输出核心，不计算相邻工作组的引导结果。`FINAL` 同样保留
两像素 band 邻域，并将已生成的引导核心及两像素邻域装入共享内存供原重建函数使用。
内区／边缘仍共用已有的保守四像素分区计划，不扩大内区或改变镜像规则。

以完整的 `8×8` 内区块计，原路径生成 144 个引导结果，新路径生成 64 个；band
计算从 256 个增加到两个步骤各 144 个。引导计算次数下降不等于整图耗时下降，新增
纹理读写、第二次 band 计算和调度成本可能抵消收益，必须按手机实测判断。

引导结果先执行原有的 `packHalf2x16`，再将四个 16-bit 位模式写入不可变 `RGBA16UI`
纹理；consumer 使用 `highp usampler2D` 读取整数位，重新组装后沿用 `unpackHalf2x16`。
不把 half 位模式当数值转换，不引入额外半精度计算，也不依赖浮点 imageStore 的舍入行为。

两层共用一张以最大所需层尺寸分配的临时纹理，只读取本层有效矩形。4096×3072
输入且两层启用时为 100663296 字节（96 MiB），处理结束和异常退出均由现有 `owned`
清理路径释放，不跨照片常驻。每次生成覆盖全部有效像素，无需读取或清空旧内容。
同一 GL 队列中用 image/texture/framebuffer barrier 完成 producer→consumer 交接和
下一层覆盖前的读写排序，不新增 CPU 回读、逐层 fence 等待或 `glFinish`。

日志保留原计时，并新增 `stage=pilot`、变体后缀 `_pilot` / `_final`、
`pilotMode=once-per-pixel`、`pilotLevels` 和 `pilotBytes`。
`stage=pilot-cache` 单独记录分配的 CPU 墙钟时间。比较每层时应把该层引导生成和重建
的内区／边缘剩余等待相加，不能仅比较 `synthesize` 就认定提速；计时仍为已有 CPU
消费点处的队列尾部，不是完整 GPU duration。诊断输出也直接复用本层引导纹理。

本次验证从修改前后真实 Kotlin 生成器导出 99／171 个 shader 变体，全部通过 GLSL
静态编译；分析、估计和解析 shader 源码逐字节不变。在 Mesa Intel Graphics (ARL)，
OpenGL ES 3.2 Mesa 26.2.4 上实际执行分配、绑定、dispatch、barrier 和回读：

- 300 组组合，覆盖 1×1、单行／单列、奇数尺寸、尾块、内区与边缘，8×8／8×16
  输出块、三种 LSC 模式、亮度／色度／双边开关、零噪声、斜坡、随机及高光交错输入。
  七层输出及 band/base/noise/pilot 共 9300 次比较、49924968 个通道值逐位一致且有限。
- 两组 4096×3072 全尺寸七层处理，覆盖随机和高光输入，两层共用同一引导纹理；
  步骤之间不插入 CPU 等待，14 次逐层输出比较、134209536 个通道值逐位一致且有限。

上述结果验证本机输出一致性，不能替代 Adreno 750 的画面及性能确认。首拍还可能
编译新增变体，需将 `stage=programs compiled>0` 与后续热拍摄分开比较。

## 多帧融合后的 IIR 扫描线分组

SABRE 和 Spatial 共用的色彩后处理器原先使用 `1×1` 工作组，一组中的一个线程
顺序扫描完整一行或一列。修改为项目既有的一维基线 `128×1` 工作组，每个线程仍
独立扫描一条完整扫描线；工作组数为 `ceil(扫描线数 / 128)`，末组多余线程在读取前
退出。横向扫描有 imageHeight 条线，纵向扫描有 imageWidth 条线，都按 global X
编号，再由原来的 linePosition 转换成图像坐标。

每条线的边界稳态、正向／反向、横向／纵向顺序、状态递推、系数、Float 表达式及
每个像素的 uint16 写回边界完整保留。IIR1、IIR2、IIR3 各自仍执行原来的四个方向，
原有 ping-pong、资源冲突等待、barrier 和导出所有权交接不变。仅将互不依赖的扫描线
合并调度，不并行拆分同一条递推链，也不重新关联浮点表达式。

新增一条 `MgcChromaTiming` 日志记录 allocation、local、iir1、error、iir2、filter、
iir3 和 final 的 CPU 墙钟时间及 `lineLanes=128`。它包含既有资源冲突等待，下一阶段
可能承担前一阶段尚未完成的等待；这些值不能当作完整的逐 shader GPU duration。
原来的 `colorNoiseIir`、`chromaFinal`、总融合耗时和降噪分层剩余等待继续保留。

## 分层计时（历史诊断，已移除）

V2329A / Adreno 750 的 `Photon_logs_20261030_190700.txt` 中，38 个 pass 的 elapsed
query 合计仅 0.018～0.021ms，而同次 HDR 输入的前序等待为 3497～4349ms。
现有证据不能确定驱动内部原因，不能用此结果排序各层瓶颈，也不能推定单位倍率进行换算。

`PhotonDenoiseTiming` 改为在输入边界及每次 analyze、estimate、resolve、synthesize
提交后插入有序 fence。提交阶段仅进行零超时轮询；所有 pass 仍按原顺序提交，不增加
逐层 CPU 等待。在已有的强度表回读、HDR 首次输入回读、Bitmap 输出回读点，按序
等待尚未完成的检查点。三轮估计按层汇总调用次数，编译和 CPU 提交耗时单独记录。

`queueTailMs` 表示到 CPU 消费点时各阶段仍未完成的队列尾部，包含 fence 等待调用
开销；提前完成的阶段为零，不代表该层没有执行成本。它不是完整 GPU duration，
因此 `gpuElapsedMs` 明确标为 `NA`，`timingMode=remaining-at-cpu-consumer`。
`syncPoint` 区分强度回读、HDR 输入、Bitmap 输出和非阻塞轮询已就绪的检查点。
失败、无法创建 fence 或释放前尚未观测的检查点分别标记状态，缺失值不合计成有效零值。
正常收集、处理失败和 EGL 资源释放路径均删除所持有的 fence。

HDR 的 `upstreamGpuWaitMs` 包含本次回读点的降噪检查点等待（`denoiseCheckpointWaitMs`）
和后续流水线等待（`pipelineRemainderWaitMs`），后者覆盖最后一个降噪检查点之后、
HDR 输入之前的工作。它们为包含关系，不可重复相加；此前强度表回读处的等待不计入此
HDR 区间。`inputMapMs` 仍单独记录 HDR 输入本身的剩余等待及复制。
`submitWallMs` 包含提交期间已有的强度表回读，与其对应的 `queueTailMs` 存在包含关系；
`cpuSubmitMs` 与 GPU 执行也存在重叠，均不能直接加成总处理时间。

本次计时修正不改 shader、dispatch 几何、参数、强度表或输出格式。新增检查点可能影响
驱动调度，包用于定位剩余等待；不把本次计时修正解释为算法提速。

内区优化包另记录 `topTile=8x8` 或 `topTile=8x16`，每个重建变体的 `i1` / `i0`
分别表示内区／边缘。两者的 `queueTailMs` 按层相加，才是该层观测到的剩余等待，
不能只比较内区数值或将编译耗时混入热拍摄结果。最高两层存在内区时增加两个检查点；
计数 `passes` 表示被测提交批次，不能据此认定算法多了滤波轮数。

## 本机验证与真机对照

从修改前后实际 Kotlin 生成器导出 32 个 shader，均通过 GLSL 编译；analyze、estimate、
resolve 的源码逐字节一致。

在 Mesa llvmpipe GLES 3.2 上，以相同输入构建金字塔并逐层对照新旧重建结果及诊断中间
结果。64 组配置覆盖 `1×1`、`2×3`、`7×9`、`8×16`、`17×19`、`37×29`、`65×33`、
`192×129`，三层／七层重建、三种 LSC 模式、不同降噪开关组合和零噪声。
1720 次比较的 5639968 个通道值逐位一致，未出现非有限值。

上述结果不替代目标 Adreno／Mali 驱动验证。手机对照应固定镜头、帧数、分辨率和降噪
参数，分别观察首次编译和后续拍摄，核对总处理时间、分层剩余等待及图像边缘、暗部
噪声和细节。测试包保留完整处理标记生命周期，不提前显示保存完成。

内区优化的独立对照使用修改前的实际 `8×16` 生成器作为基准，新生成器覆盖两种输出
分块、两种边界变体和所有有效降噪开关组合。新旧共 126 个 shader 通过 GLSL 编译；
analyze、estimate、resolve 源码逐字节不变。实际 Kotlin 分区实现的 67600 组尺寸／
分块／开关计划逐个验证工作组无空洞、无重叠及四像素安全邻域。

本机 EGL 实际选择 NVIDIA GeForce RTX 5070 Ti Laptop GPU / GLES 3.2 / 615.71.09。
在该驱动上 dispatch、barrier、回读并比较最终重建与 band/base/noise/pilot 中间结果，
360 组配置、3240 次比较、33033744 个通道值逐位一致且有限。覆盖三种 LSC 模式、
零噪声、全部有效降噪开关组合及 `1×1`、`2×3`、`7×9`、`8×16`、`17×19`、
`24×36`、`37×29`、`65×33`、`97×81`、`129×101`。这是本机正确性验证，不能
替代手机上的画面检查，也不用于预测 Adreno 性能。

梯度共享实验曾在相同本机 GLES 驱动上通过 360 组配置、3240 次比较，33033744 个
最终重建／诊断中间通道值与原算法逐位一致且有限。但下述实机结果显示性能回退，
该实验代码已移除，重建恢复到已验证的 `8×8` 内区实现。

IIR 从修改前后真实 Kotlin 文件导出全部十个色彩 shader。除两个 IIR shader 的
local_size 与 outer 编号外，其他 shader 和三组实际缩放系数逐字节一致，递推算术
源码不变，均通过 GLSL 和 GLES 3.1 工作组基线检查。在本机 GLES 驱动逐方向比较
IIR1→IIR2→IIR3 的十二个处理步骤，132 组输入、1584 次比较、86988096 个 uint16
通道值逐位一致。覆盖缩放 1 / 1.5 / 2，零值、极值、随机色度、阶跃／脉冲，以及
`1×1`、`1×17`、`17×1`、`7×9`、`33×129`、`129×33`、`129×131`、`257×259`、
`513×67`、`4096×3`、`3×4096`，包含 128 条线不能整除的尾组和完整 4096 像素递推链。
这些检查不替代目标手机的驱动、画面及性能验证。

`Photon_logs_20261030_230600.txt` 对应同时启用梯度共享和 IIR 分组的测试包。
三张均为缓存命中、专业模式、1 倍、两帧、4096×3072，处理时间为 4406 / 4015 /
4165ms，均值 4195.3ms。相对上一 `8×8` 热拍摄样本，色彩 IIR 的 CPU 提交／资源
等待区间均值由 811ms 降至 202ms，SABRE 总融合由 1358.5ms 降至 707ms；但最高层
重建剩余等待由 1142.6ms 增至 1465.1ms，次高层由 246.3ms 增至 317.7ms。
因此保留 IIR 分组，移除梯度共享，以恢复原重建作为单变量确认；该组合的最终收益
仍需新包实测，不能把运算次数减少直接换算为手机提速，也不凭此推定具体硬件瓶颈。

## 自动预热现状

已有入口在首个预览帧后延迟 1000ms 触发，要求照片模式、预览活动、没有正在拍摄，
并避开低内存、省电和中等以上热限制。按快门会取消预热协程的后续任务。
`RawDemosaicProcessor.prewarmCapturePipeline` 当前预热测光与显影路径，但没有准备
按需生成的 Photon 重建变体，所以首拍仍可能出现 `stage=programs compiled=7`。
一次记录的 510ms 编译可作为补齐预热的目标，不能当作每张照片计算的可消除部分。

本次未扩展预热逻辑。补齐时应复用实际拍摄的 EGL context 和 program 缓存，只准备
当前模式缺失的变体，按变体分批检查取消；必要的试运行使用小尺寸、已初始化的合成
输入，不运行整张 12MP 管线，不采集照片或写入相册。预热会短时争用 CPU/GPU、
增加耗电和缓存内存；不能立即打断驱动内已开始的单次 compile/link，不能保证用户
刚打开就按快门时完全消除首拍初始化等待。退出预览和资源重建的生命周期也应闭合。
